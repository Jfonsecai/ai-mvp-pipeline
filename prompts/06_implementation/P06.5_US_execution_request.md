# P06.5 — Request to Execute One User Story

**Version:** 1.0
**Phase:** P06 — Implementation
**Type:** Execution wrapper for P06.3
**Execution mode:** One selected user story per request

## 1. Purpose

Use this prompt when a user asks in chat to implement a specific user story (HU). It turns that
request into an implementation task: inspect the current project context, follow
`prompts/06_implementation/P06.3_US_implementation.md`, modify and verify the actual code, and
continue to the independent P06.4 validation when P06.3 permits it.

This prompt supplements P06.3; it does not replace or weaken its requirements, quality gates,
implementation boundaries, or required outputs.

## 2. Request and Scope

The user must identify exactly one HU by its canonical ID, for example `US-022`.

* If the user names exactly one valid HU, implement that HU; do not stop after returning a plan,
  analysis, or suggested command.
* If the user does not provide an HU ID, ask which single HU to implement before changing files.
* If the user requests multiple HUs, explain that each needs a separate P06.3 execution and ask
  which one to start with. Do not implement multiple HUs in one execution.
* Preserve the ID, title, acceptance criteria, business rules, edge cases, and dependencies from
  the current authoritative backlog. Do not infer the requested story from a title alone.

## 3. Required Context

Read and follow these inputs before editing:

1. `prompts/system/SYSTEM_PROMPT.md`.
2. `prompts/06_implementation/P06.3_US_implementation.md` in full. Follow its preconditions,
   implementation process, verification, logging, index, and reporting requirements.
3. Current requirements and authoritative requirements backlog:
   * `artifacts/02_requirements/REQUIREMENTS_V4.md`
   * `artifacts/02_requirements/product_backlog_requirements_v4.json`
   * `artifacts/02_requirements/REQUIREMENTS_VALIDATION_V4.md`
4. Current planning and iteration scope:
   * `artifacts/03_planning/PRIORITIZATION_V3.md`
   * `artifacts/03_planning/product_backlog_priori_v3.json`
   * `artifacts/03_planning/PRIORITIZATION_VALIDATION_V3.md`
5. Current UX and its validation:
   * `artifacts/04_ux/UX_SPEC_V3.md`
   * `artifacts/04_ux/UX_SPEC_VALIDATION_V3.md`
6. Current architecture, API contract, data model, and validations:
   * `artifacts/05_architecture/ARCHITECTURE_V4.md`
   * `artifacts/05_architecture/ARCHITECTURE_VALIDATION_V4.md`
   * `artifacts/05_architecture/API_SPEC_V2.yaml`
   * `artifacts/05_architecture/DATA_MODEL_V1.md`
7. `artifacts/03_planning/CHANGE_REQUEST_CR-P06-001.md` if it affects the selected HU or its
   referenced requirements.
8. Current implementation state:
   * `artifacts/06_implementation/FOUNDATION_VALIDATION.md`
   * `artifacts/06_implementation/IMPLEMENTATION_LOG.md`
   * `artifacts/06_implementation/IMPLEMENTATION_INDEX.md`, if present
   * Implementation logs and validation reports for the selected HU and its dependencies, if any
   * The actual source code, tests, migrations, configuration, and relevant documentation
9. `prompts/06_implementation/P06.4_US_validation.md` for the required next validation step.

The paths above identify the latest project artifacts at the time this prompt was created. Before
using them, inspect the repository for newer versions and read the version/status metadata and
validation results. Use the newest approved, relevant artifact set; do not choose a version based
only on its filename or mix versions without checking consistency. If a newer applicable artifact
exists, use it and state which sources were selected. Do not silently fall back to an older version
when a required current artifact is missing or invalid.

Use `product_backlog_requirements_v4.json` (or its verified newer successor) to resolve the
authoritative HU definition and acceptance criteria. Use the planning backlog and prioritization
documents for sprint, priority, and delivery status. If these or any approved sources conflict,
follow P06.3: document the conflict and its impact, and stop as `BLOCKED` if it prevents safe
implementation.

## 4. Execution Instructions

1. Locate the exact requested HU in the authoritative backlog and record its full scope, criteria,
   business rules, edge cases, dependencies, and status.
2. Assess foundation readiness, validation conditions, UX/architecture completeness, and dependency
   availability according to P06.3. Do not start code changes if a material blocker prevents safe
   implementation; document it and report `BLOCKED`.
3. Inspect the current implementation and tests. Verify whether any part of the selected HU already
   exists; distinguish partial/shared functionality from criteria actually satisfied. Do not
   duplicate existing behavior or declare the HU complete based only on similarly named code.
4. Implement the selected HU as a complete vertical slice where its criteria require it. Keep changes
   limited to this HU and necessary integration. Preserve unrelated work and existing behavior.
5. Add or update relevant tests, run the focused checks and regression checks required by P06.3,
   and report exact outcomes. Do not claim unrun checks passed.
6. Produce the HU-specific implementation log and update the cumulative implementation index as
   P06.3 requires. Preserve historical validation reports and unrelated entries. If a historical
   implementation record must remain immutable, create a clearly versioned follow-up record in
   `artifacts/06_implementation/increments/` and point the index to the current record; do not
   erase or rewrite evidence to conceal prior outcomes.
7. If P06.3 finishes with `READY_FOR_VALIDATION` or `READY_WITH_LIMITATIONS`, continue with
   `P06.4_US_validation.md` for the same HU ID when the current validation prerequisites are
   available. Keep implementation and validation outcomes separate. If validation cannot proceed,
   explain why and identify it as pending; never describe an implementation log as independent
   validation.
8. Create new files only in their appropriate project folders. Do not edit this prompt, P06.3, or
   prior requirement, planning, UX, architecture, or validation artifacts to make the implementation
   appear consistent.

## 5. Final Response

Report concisely:

* The HU ID and title implemented, or the exact reason it is `BLOCKED`.
* The key code/test files changed, with workspace links.
* Focused tests/checks run and their actual results.
* Implementation-log and index updates.
* P06.4 validation status, if executed; otherwise state that it remains pending and why.
* Any remaining acceptance criteria, assumptions, warnings, or blockers.
