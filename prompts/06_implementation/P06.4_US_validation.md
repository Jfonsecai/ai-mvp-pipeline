# P06.4 — Incremental User Story Validation

**Version:** 1.0
**Phase:** P06 — Implementation
**Type:** Independent implementation validation
**Execution mode:** Validate one selected user story per execution

## 1. Objective

Independently validate whether the implementation of one selected user story satisfies its approved acceptance criteria, applicable business rules, edge cases, requirements, architectural constraints, and UX expectations.

The validation must inspect the actual repository and execute relevant checks when feasible. It must not rely exclusively on the implementation log, developer claims, or the existence of code and tests.

Each execution validates exactly one HU, identified by its canonical backlog ID, such as `US-020`.

**P06.4 validates the selected implementation increment. It does not replace P07, which is responsible for broader product testing.**

## 3. Authoritative Sources and Validation Principles

Use each source according to its purpose:

* `product_backlog.json` is authoritative for the selected HU's acceptance criteria, business rules, edge cases, dependencies, and current backlog definition.
* `REQUIREMENTS.md` provides the approved functional and non-functional requirements.
* `PRIORITIZATION.md` provides priority, sprint, and delivery context.
* `ARCHITECTURE.md` defines approved technical constraints and design decisions.
* `ARCHITECTURE_VALIDATION.md` records the architecture's approval status and conditions.
* `UX_SPEC.md` and its validation report define the applicable interface and interaction expectations.
* `FOUNDATION_VALIDATION.md` establishes whether the technical foundation was approved.
* The HU implementation log describes the intended changes and reported evidence.
* The actual repository and executed checks provide evidence of implementation behavior.
* Prior validation reports provide context for dependencies and previously identified issues.

Apply these principles:

1. **Independent verification:** verify implementation claims against code and observed behavior.
2. **Acceptance-criteria coverage:** assess every applicable acceptance criterion individually.
3. **Evidence-based conclusions:** support material findings with files, code locations, test output, or observed behavior.
4. **Architecture conformance:** evaluate the implementation against approved decisions.
5. **Scope discipline:** validate the selected HU and necessary integration, not the entire product backlog.
6. **No invented requirements:** do not impose behavior absent from authoritative artifacts.
7. **Honest test reporting:** distinguish executed checks from unexecuted checks, assumptions, and inferred risks.
8. **Actionable findings:** identify what is wrong, why it matters, and what evidence would demonstrate a correction.
9. **No silent scope changes:** do not approve altered acceptance criteria as if they were the original requirements.
10. **Preservation of history:** do not delete or rewrite previous evidence to conceal failures.

## 4. Preconditions and Blocking Conditions

Before validation:

1. Confirm that the foundation validation permits incremental development.
2. Confirm that the selected HU exists in the current backlog.
3. Verify that the implementation log corresponds to the HU and the repository state being examined.
4. Inspect any known dependency conditions that affect the selected HU.
5. Identify missing artifacts or unresolved decisions that materially affect the validation.

Use `BLOCKED` when a missing prerequisite, unresolved material decision, unavailable dependency, or insufficient evidence prevents a reliable validation decision.

Do not use `BLOCKED` merely because an optional test tool or external service is unavailable. Perform feasible checks and document the limitation if a meaningful assessment remains possible.

Do not treat a missing implementation log as proof that no code exists. Inspect the repository when possible, but report the missing traceability artifact and assess whether it prevents reliable validation.

## 5. Validation Scope and Criteria

### 5.1 Acceptance Criteria

Validate every acceptance criterion defined for the selected HU in the authoritative backlog.

For each criterion, assess:

* Whether the required behavior is implemented.
* Whether the implementation corresponds to the original criterion.
* Whether the behavior can be verified through code inspection, automated tests, manual execution, or another suitable method.
* Whether the available evidence demonstrates that the criterion is satisfied.
* Whether relevant failure paths and edge conditions are handled.
* Whether the criterion remains incomplete, unverified, or blocked.

Do not infer that a criterion passes merely because a related function, component, endpoint, database field, or test file exists.

A criterion that has not been verified must not be reported as passed.

### 5.2 Functional Behavior and Business Rules

Verify the implemented behavior against the selected HU's story description, applicable requirements, and business rules.

Inspect, as applicable:

* Input validation.
* Required fields and constraints.
* Business logic and state transitions.
* Persistence and retrieval.
* Error handling and failure behavior.
* Authorization and access control, when required.
* API responses and contracts.
* UI feedback and interaction behavior.
* Integration between relevant layers.
* Handling of applicable edge cases.

Do not invent expected behavior when a business rule or edge case is unresolved. Identify the ambiguity and determine whether it prevents a reliable conclusion.

### 5.3 UX and Interaction Conformance

When the HU affects the user interface, evaluate relevant behavior against the approved UX specification.

Inspect applicable elements such as:

* Navigation and entry points.
* User inputs and required fields.
* Validation feedback.
* Success and error states.
* Loading or empty states, when specified.
* Displayed information and interaction outcomes.
* Consistency with the approved flow.

Do not require visual or interaction behavior that is not specified or reasonably implied by the approved sources. Record subjective design improvements separately from compliance defects.

### 5.4 Architecture and Integration

Verify that the increment:

* Uses the appropriate architectural layers and components.
* Respects approved module boundaries and dependencies.
* Integrates correctly with existing shared infrastructure.
* Uses the agreed data and API contracts.
* Avoids unnecessary duplication or incompatible parallel implementations.
* Does not introduce material unapproved architectural changes.
* Preserves existing behavior outside the intended change, to the extent supported by relevant checks.

If a deviation is necessary, determine whether it was approved. Do not silently accept a material architectural change merely because the implementation appears functional.

### 5.5 Persistence and Data Integrity

When applicable, verify:

* Data is stored and retrieved according to the criterion.
* Required fields and constraints are enforced appropriately.
* Database migrations or schema changes are coherent.
* Relationships and references are handled correctly.
* Relevant invalid or missing data cases are handled.
* The implementation does not introduce obvious data-integrity or consistency problems.

Do not require persistence functionality for a HU that does not need it.

### 5.6 Security and Error Handling

Evaluate relevant security and error-handling behavior, including:

* Validation of untrusted inputs.
* Authentication and authorization where applicable.
* Exposure of sensitive information.
* Handling of invalid requests and expected failures.
* Safe treatment of configuration and secrets.
* Appropriate error responses and user feedback.

Do not require unrelated security features that are outside the HU and approved architecture. However, a critical security or data-integrity defect introduced by the increment can prevent approval even if the main happy path works.

### 5.7 Automated Tests and Regression Checks

Inspect the tests associated with the selected HU and run appropriate checks when feasible.

Evaluate:

* Whether tests correspond to the relevant acceptance criteria.
* Whether assertions check meaningful behavior rather than merely execution.
* Whether the tests are actually executed.
* Whether failures are attributable to the increment, existing code, or environmental limitations.
* Whether relevant existing tests reveal regressions.
* Whether important behaviors remain unverified.

Do not assume that tests are adequate simply because they pass. Review their relevance and assertions.

Do not require the entire P07 testing suite at this stage. Run targeted tests and appropriate regression checks for the increment.

### 5.8 Implementation Log Accuracy and Traceability

Verify that the HU implementation log:

* Uses the canonical HU ID.
* References the correct requirements and acceptance criteria.
* Accurately lists significant changes.
* Reports test results honestly.
* Documents assumptions, deviations, and limitations.
* Uses a status consistent with the observed implementation.
* Provides enough information to reproduce relevant checks.

Report material differences between the log and the actual repository.

### 5.9 Scope and Side Effects

Confirm that the implementation is limited to the selected HU and justified integration work.

Review whether:

* Unrelated user stories were implemented unintentionally.
* Shared functionality was changed unnecessarily.
* Existing behavior was broken by the increment.
* The change introduces unnecessary dependencies or scaffolding.
* Changes outside the HU's scope have an explicit justification.

Do not fail an increment simply because other user stories remain unimplemented.

### 5.10 Dependency Readiness

Where the selected HU depends on other stories, shared modules, or external components, verify that those dependencies are available and compatible with the expected behavior.

Consult prior validation reports when necessary.

If a dependency is unresolved or unavailable, determine whether the selected HU can still be validated independently. If not, report `BLOCKED` rather than treating the missing dependency as a successful integration.

## 6. Evidence and Finding Severity

Every material finding must include:

* A unique finding identifier.
* A concise title.
* Severity.
* The affected HU and acceptance criterion, when applicable.
* The validation criterion.
* Evidence, such as a file path, code location, command output, test result, or observed behavior.
* Why the finding matters.
* The corrective action required.
* The verification needed to close the finding.

Use the following severity levels:

* `CRITICAL` — a critical security, data-integrity, or functional failure; or a defect that makes the implementation unsafe or fundamentally unusable for its intended behavior.
* `HIGH` — a required acceptance criterion is materially unsatisfied, an important business rule is violated, or a significant integration failure prevents the HU from working as intended.
* `MEDIUM` — a meaningful defect or incomplete behavior exists, but it does not necessarily invalidate the entire HU.
* `LOW` — a minor defect or limited-impact issue.
* `INFO` — a traceability note, observation, or non-mandatory recommendation.

Distinguish mandatory corrections from optional improvements. Do not invent line numbers or test results. If precise code locations are unavailable, reference the relevant file or component and explain the evidence.

Severity must reflect actual impact, not the number of findings.

## 7. Validation Process

### Step 1 — Establish the validation target

Identify the exact HU ID and load its authoritative definition from `product_backlog.json`.

Verify that the implementation log corresponds to the same HU and that its criteria references are consistent with the backlog.

### Step 2 — Establish expected behavior

Extract the original acceptance criteria, relevant requirements, business rules, edge cases, UX constraints, and dependencies.

Identify any ambiguity that could affect a pass/fail decision.

### Step 3 — Inspect the repository

Review the actual implementation, relevant tests, configuration, and change set when available.

Identify the files and components that implement each criterion.

Do not rely exclusively on the implementation log or summaries.

### Step 4 — Execute relevant checks

Run the appropriate available checks, such as:

* Build or compilation.
* Unit tests.
* Integration tests.
* API or component tests.
* Database or migration checks.
* Frontend tests.
* Targeted regression tests.
* Manual verification of relevant flows, where feasible.

Record commands and actual results.

If a check cannot be executed, document why, its impact, and whether alternative evidence is sufficient. Do not mark it as passed.

### Step 5 — Evaluate each acceptance criterion

For every criterion, determine whether the available evidence supports satisfaction.

Separate:

* Verified behavior.
* Implemented but unverified behavior.
* Partially implemented behavior.
* Missing behavior.
* Blocked behavior.

### Step 6 — Evaluate risks and integration

Review applicable business rules, edge cases, architecture, UX, security, persistence, integration, and regression risks.

Identify any material unapproved deviation or unintended scope expansion.

### Step 7 — Reconcile implementation records

Compare the actual repository with the implementation log and the current implementation index.

Record any mismatch, missing evidence, or incorrect status.

### Step 8 — Determine the final status

Apply the decision rules in Section 9. Do not approve the HU solely because its primary happy path works if a required acceptance criterion remains materially unsatisfied.

### Step 9 — Produce the HU-specific validation report

Create or update:

`artifacts/06_implementation/increments/US-XXX_IMPLEMENTATION_VALIDATION.md`

Replace `US-XXX` with the exact canonical HU ID.

The report must preserve the history of the validation attempt. If a prior report exists, update it only in a way that retains prior results and clearly identifies the latest decision; alternatively, create a versioned report and update the index to point to the latest report. Never erase historical failures or warnings.

### Step 10 — Update the implementation index

Create or update:

`artifacts/06_implementation/IMPLEMENTATION_INDEX.md`

Update only the selected HU's validation status, report reference, outstanding issues, and last-updated information. Preserve all other HU entries.

## 8. Required Output A: HU Implementation Validation Report

The file `US-XXX_IMPLEMENTATION_VALIDATION.md` must contain the following sections.

### 8.1 Metadata

Include:

* Phase and prompt identifier.
* Version.
* Validation date, if available.
* HU ID and title.
* Backlog source path.
* Implementation log path.
* Relevant requirements, acceptance criteria, business rules, and dependency IDs.
* Foundation validation status.
* Implementation status reported by P06.3.
* Final validation status.

### 8.2 Executive Summary

Summarize:

* What was validated.
* Whether the implementation satisfies the HU's required behavior.
* The most important findings.
* Whether the HU is approved, approved with warnings, failed, or blocked.
* Any conditions that must be resolved before proceeding.

### 8.3 Validation Scope and Limitations

Identify:

* The functionality examined.
* The acceptance criteria included.
* The tests and checks executed.
* Any criteria or behaviors that could not be verified.
* Any environmental or dependency limitations.

Explicitly state that this is HU-level validation and not final product-wide testing.

### 8.4 Acceptance Criteria Validation Matrix

Include one row for every acceptance criterion from the authoritative backlog.

Use the following fields:

| Field                   | Description                                     |
| ----------------------- | ----------------------------------------------- |
| Criterion ID            | Original acceptance criterion ID                |
| Expected behavior       | Original criterion or faithful reference        |
| Implementation evidence | Relevant files or components                    |
| Verification method     | Test, command, code inspection, or manual check |
| Result                  | `PASS`, `FAIL`, `NOT_VERIFIED`, or `BLOCKED`    |
| Evidence                | Actual result or explanation                    |
| Findings                | Related finding IDs, if any                     |

Do not omit a criterion because it was not implemented or could not be tested.

A criterion is `PASS` only when sufficient evidence supports its satisfaction.

### 8.5 Business Rules, Edge Cases, and Dependencies

For each applicable rule, edge case, and dependency, report:

* Identifier.
* Expected behavior or dependency condition.
* Evidence reviewed.
* Result.
* Findings or remaining limitations.

Do not invent expected behavior for unresolved rules.

### 8.6 Test and Verification Results

For every executed check, document:

* Check name.
* Command or procedure.
* Result.
* Relevant output or evidence.
* Limitations.

Use `PASSED`, `FAILED`, `NOT_RUN`, or `BLOCKED` for individual checks.

Distinguish test execution from test coverage. A passing test suite does not automatically prove that every acceptance criterion is satisfied.

### 8.7 Architecture, UX, and Integration Conformance

Summarize relevant conformance with the approved architecture and UX specification.

Identify material deviations, integration problems, and any approval required.

If a dimension does not apply to the selected HU, state that it was not applicable rather than inventing a requirement.

### 8.8 Security, Data Integrity, and Regression Findings

Report applicable defects or risks, the evidence reviewed, and their impact.

Distinguish observed defects from risks that could not be conclusively verified.

### 8.9 Findings Register

List all material findings with their identifiers, severity, evidence, impact, corrective actions, and closure criteria.

Separate mandatory corrections from optional recommendations.

If no material findings exist, state this explicitly and describe the scope of the evidence reviewed.

### 8.10 Implementation Log Consistency

Document any differences between the implementation log and the actual repository or verification results.

Confirm whether the log's reported status is consistent with the evidence.

### 8.11 Readiness Decision

Explain whether the selected HU is ready to be considered validated, including any non-blocking warnings and required conditions.

Do not imply that the entire product is ready for release based on one HU's validation.

### 8.12 Final Status

Choose exactly one status:

* `PASS` — all required acceptance criteria are supported by sufficient evidence, relevant business rules and required dependencies are satisfied, and no material defect prevents accepting the increment.
* `PASS_WITH_WARNINGS` — the HU satisfies its required acceptance criteria, but documented non-blocking risks, limitations, or minor issues remain. Explicitly state any required follow-up conditions.
* `FAIL` — one or more required acceptance criteria are materially unsatisfied, a material defect is present, or a significant unapproved deviation prevents accepting the increment.
* `BLOCKED` — a missing prerequisite, unresolved material decision, unavailable dependency, or insufficient evidence prevents a reliable validation decision.

Do not use `PASS_WITH_WARNINGS` to bypass an unsatisfied required criterion or a material defect.

### 8.13 Corrective Actions and Retest Guidance

For each failed or blocking finding, describe:

* Required correction.
* Related acceptance criterion or requirement.
* Verification procedure.
* Evidence needed for closure.

If the status is `FAIL`, the implementation must be corrected and validated again. If `BLOCKED`, resolve the blocker before attempting a conclusive validation.

## 9. Decision Rules and Pipeline Transition

Apply the following rules:

* `PASS`: record the HU as validated and assess whether the next planned HU is ready, considering dependencies and prioritization.
* `PASS_WITH_WARNINGS`: record the HU as validated with warnings only if all required acceptance criteria pass and the remaining issues do not prevent safe progress. Track required follow-up conditions.
* `FAIL`: do not treat the HU as complete. Correct the implementation and repeat P06.4 for the same HU.
* `BLOCKED`: resolve the prerequisite or evidence blocker before making a final acceptance decision.

A passing HU does not automatically authorize implementation of any arbitrary next story. Before the next P06.3 execution, select the next HU according to the current backlog and planning artifacts, and verify its dependencies.

After the planned implementation scope has been completed and the pipeline's other required conditions are satisfied, proceed to P07 for broader product testing.

P06.4 does not replace P07, CI/CD validation, or release readiness assessment.

## 10. Required Output B: Updated Implementation Index

Update `artifacts/06_implementation/IMPLEMENTATION_INDEX.md`.

For the selected HU, maintain at least:

* HU ID.
* HU title.
* Priority or sprint, when defined.
* Latest implementation status.
* Latest validation status.
* Implementation log path.
* Latest validation report path.
* Outstanding blockers or warnings.
* Last-updated date, when available.

Rules:

* Preserve all other HU entries.
* Do not change the implementation status unless supported by the current implementation log.
* Do not mark an HU `PASS` based on P06.3's status.
* Update validation status only from the validation actually performed.
* Keep the report reference synchronized with the latest validation report.
* Preserve the history of prior failed, blocked, or warning-bearing validations.
* If the index does not exist, initialize it from available implementation logs and validation reports. Clearly identify any entries whose historical status cannot be confirmed.

* [ ] Every acceptance criterion was included in the validation matrix.
* [ ] Applicable business rules, edge cases, and dependencies were evaluated.
* [ ] The actual repository was inspected.
* [ ] Relevant checks were executed where feasible.
* [ ] Executed and unexecuted checks are clearly distinguished.
* [ ] Findings include evidence, severity, impact, and corrective action.
* [ ] Optional recommendations are distinguished from mandatory corrections.
* [ ] The implementation log was compared with actual evidence.
* [ ] The final status follows the defined decision rules.
* [ ] The HU-specific validation report was created or updated.
* [ ] The cumulative implementation index was updated without removing unrelated entries.
* [ ] The report does not imply that P07 or whole-product testing has been completed.

The final report must be evidence-based, traceable to the authoritative HU, and explicit about what was and was not verified.
