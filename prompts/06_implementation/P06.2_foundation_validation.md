# P06.2 — Foundation Validation

**Version:** 1.0
**Phase:** P06 — Implementation
**Type:** Independent code and foundation validation
**Execution mode:** One-time validation gate after P06.1

## 1. Objective

Independently validate whether the technical foundation implemented in P06.1 conforms to the approved architecture, is sufficiently coherent and secure, and is ready to support incremental user-story implementation.

The validation must examine the **actual repository state**, not merely trust the implementation log or the implementation prompt's reported status.

This validation evaluates the technical foundation. It does not require the product's user stories to be implemented and must not penalize the repository for missing story-specific functionality that is explicitly outside the scope of P06.1.

## 2. Required Inputs

Read and inspect:

1. `prompts/system/SYSTEM_PROMPT.md`
2. `artifacts/05_architecture/ARCHITECTURE.md`
3. `artifacts/05_architecture/ARCHITECTURE_VALIDATION.md`
4. `artifacts/03_planning/PRIORITIZATION.md`
5. `artifacts/03_planning/product_backlog.json`
6. `artifacts/04_ux/UX_SPEC.md`
7. `artifacts/04_ux/UX_SPEC_VALIDATION.md`
8. `artifacts/06_implementation/IMPLEMENTATION_LOG.md`
9. The actual repository structure, source code, dependency manifests, configuration files, scripts, and relevant documentation.

If any required artifact is missing, unreadable, or inconsistent, document the issue and assess whether validation can continue reliably.

The architecture is the primary reference for technical conformance. Its validation report determines whether its approval conditions and blockers have been addressed. Planning, backlog, and UX artifacts provide context for evaluating whether the foundation supports the approved product direction; they do not authorize requiring unimplemented user stories.

## 3. Validation Principles

Apply the following principles:

1. **Inspect the actual implementation:** do not accept claims in the implementation log without evidence.
2. **Architecture conformance:** evaluate the implementation against approved architectural decisions.
3. **Foundation scope:** validate only the technical foundation expected in P06.1.
4. **Traceability:** connect findings to relevant architecture sections, implementation files, configuration, commands, or observed behavior.
5. **No invented requirements:** do not fail the implementation because of a preference or technical choice that the approved sources do not require.
6. **Security and reproducibility:** examine configuration safety and whether the documented setup and verification steps are credible.
7. **Honest evidence:** distinguish observed facts, executed checks, inferred risks, and unverified claims.
8. **Proportionality:** prioritize issues that affect safe startup, maintainability, architecture conformance, security, or the ability to implement user stories incrementally.
9. **Independent assessment:** the generator's status does not determine the validation result.
10. **Actionable findings:** explain what must change, why it matters, and how the finding can be verified.

Do not silently approve a deviation that requires architectural approval.

## 4. Preconditions and Blocking Conditions

Before reviewing the code:

1. Confirm that the required artifacts are available.
2. Review the architecture validation report and its unresolved conditions.
3. Identify any unresolved critical architectural blockers.
4. Confirm that the implementation log corresponds to the repository state being inspected.

If the architecture is not approved, a critical architectural decision remains unresolved, or a missing input prevents reliable assessment, use `BLOCKED` when the validation cannot responsibly reach a conclusion.

Do not use `BLOCKED` merely because an optional tool or external service is unavailable. If reliable partial validation is possible, perform it and document the limitation; determine the final status according to the impact of the missing verification.

## 5. Validation Scope and Criteria

### 5.1 Architecture Conformance

Verify that:

* The implemented structure reflects the approved architecture.
* Major modules and their responsibilities are consistent with the architecture.
* Module boundaries and dependencies are reasonable and consistent with the documented design.
* The chosen frameworks, runtimes, persistence approach, communication mechanisms, and infrastructure match approved decisions where specified.
* Any deviation is documented and has the required approval.
* No material unapproved architectural decision has been introduced.

Do not require a specific technical choice if the architecture leaves it open and the implementation's choice is reasonable, documented, and compatible with the approved design.

### 5.2 Project Structure and Maintainability

Inspect:

* Directory and module organization.
* Separation of responsibilities.
* Naming and repository conventions.
* Dependency organization.
* Duplicate or unnecessary scaffolding.
* Unused modules or placeholder code with no justified purpose.
* Whether the foundation can be extended without avoidable restructuring.

Do not fail the foundation for minor stylistic preferences that do not materially affect maintainability or conformance.

### 5.3 Runtime, Build, and Startup

Verify, when the environment permits:

* Dependency manifests and configuration are coherent.
* The project can install dependencies or otherwise resolve its declared requirements.
* The application builds, compiles, or starts using the documented process.
* Entry points and startup configuration are valid.
* Relevant technical checks execute as documented.
* Failures and environment limitations are identified accurately.

Do not mark an unexecuted check as passed. If a check cannot be run, record the limitation and assess its significance.

### 5.4 Persistence and External Integrations

When required by the architecture, inspect:

* Database and persistence configuration.
* Connection configuration and environment-variable handling.
* Separation between application code and infrastructure details.
* Configuration for required external services.
* Whether connection or integration checks can be executed safely.
* Whether unavailable services are documented rather than represented as verified.

Do not require populated product tables, story-specific repositories, complete business transactions, or production data when these are outside the foundation scope.

### 5.5 API, Frontend, and Application-Layer Foundations

Evaluate only the components applicable to the approved architecture.

For an API or backend, inspect relevant routing, application entry points, shared middleware, error handling, and module organization.

For a frontend, inspect the application entry point, routing or navigation foundation, configuration, and the structure needed to add screens incrementally.

For a multi-component application, verify that the agreed components have a coherent integration approach.

Do not require functional user-story endpoints, complete screens, or end-to-end business flows at this stage.

### 5.6 Security and Configuration

Inspect, as applicable:

* Secrets and credentials are not committed in source files or example configuration.
* Sensitive configuration is handled through appropriate environment or configuration mechanisms.
* Development defaults do not introduce obvious avoidable security risks.
* Error handling and logging do not unnecessarily expose secrets or sensitive information.
* Authentication, authorization, CORS, and other security mechanisms are configured when required by the approved architecture.
* Dependencies and configuration do not introduce evident critical risks.

Do not require complete story-specific authorization policies if the relevant functionality is not yet implemented. However, do not accept a foundation that exposes existing sensitive functionality or violates an explicit architectural security requirement.

### 5.7 Logging, Errors, and Operational Foundations

Verify the presence and coherence of shared logging, error-handling, diagnostics, health checks, or equivalent mechanisms when they are required or explicitly included in the architecture.

Check that the implementation log accurately describes what is present.

Do not impose additional observability infrastructure merely because it might be useful in a larger production system.

### 5.8 Readiness for Incremental Development

Assess whether:

* The foundation can accommodate the planned product scope without contradicting the approved architecture.
* Developers can identify where new functionality belongs.
* Shared infrastructure and integration boundaries are sufficiently clear.
* The documented setup and verification steps allow the team to begin implementing user stories.
* Known assumptions and unresolved dependencies are visible and manageable.
* No structural blocker prevents incremental implementation.

This criterion evaluates technical readiness, not completion of the backlog.

### 5.9 Scope Boundary: Foundation Versus User Stories

Explicitly verify that P06.1 has not silently implemented user-story functionality.

The absence of business features is expected and must not be reported as a defect.

If story-specific behavior exists, determine whether it is a legitimate minimal technical verification mechanism or out-of-scope implementation. Document any material scope violation.

Use the backlog and UX specification to understand future integration needs, not to demand that their functionality already exist.

### 5.10 Traceability and Implementation Log Accuracy

Check whether `IMPLEMENTATION_LOG.md`:

* Identifies the inputs used.
* Accurately describes implemented components and repository changes.
* Documents architectural deviations, assumptions, and unresolved issues.
* Reports checks and their results honestly.
* Provides usable setup and execution instructions.
* States a final status consistent with the observed repository.

Report missing, contradictory, or unsupported claims.

## 6. Evidence and Severity

Every material finding must include:

* A unique finding identifier.
* A concise title.
* Severity.
* The affected criterion.
* Evidence: file path, configuration, relevant code location, command output, or observed behavior.
* Why the issue matters.
* The corrective action required.
* The verification needed to close the finding.

Use these severity levels:

* `CRITICAL` — prevents safe or reliable use of the foundation, violates a critical architectural constraint, or introduces a critical security or integrity issue.
* `HIGH` — materially prevents foundation readiness, violates an important approved decision, or blocks incremental development.
* `MEDIUM` — creates a meaningful risk or maintainability problem but does not necessarily prevent incremental development.
* `LOW` — minor issue or improvement with limited impact.

Do not invent line numbers or execution results. If precise code locations are unavailable, cite the file or component and describe the observed issue.

Distinguish defects from recommendations. An optional improvement must not be presented as a mandatory architectural requirement.

## 7. Validation Process

### Step 1 — Inspect inputs and repository state

Read the required artifacts and inspect the actual files.

Confirm that the implementation log describes the repository being validated.

### Step 2 — Establish the applicable requirements

Extract the architectural decisions and conditions relevant to the foundation.

Identify which checks are required by the approved architecture, which are justified by the implementation log, and which are optional recommendations.

### Step 3 — Inspect the implementation

Review the relevant code, project structure, dependencies, configuration, integration points, and documentation.

Do not rely exclusively on summaries or self-reported results.

### Step 4 — Execute feasible checks

Run appropriate verification commands when permitted and feasible.

Record the exact checks performed and their results. When execution is unavailable, explain why and evaluate whether the missing evidence affects the final decision.

### Step 5 — Evaluate readiness and scope

Assess architecture conformance, security, configuration, maintainability, operational foundations, reproducibility, traceability, and readiness for incremental development.

Do not score the foundation based on the absence of user stories.

### Step 6 — Reconcile the implementation log

Compare reported files, components, decisions, and test results with the repository and observed evidence.

Identify inaccuracies, omissions, and unsupported claims.

### Step 7 — Determine the validation status

Choose the status according to the criteria in Section 9.

### Step 8 — Produce the validation report

Create or update:

`artifacts/06_implementation/FOUNDATION_VALIDATION.md`

The report must be sufficient for the team to understand the decision, correct the findings, and determine whether the foundation can be used for incremental implementation.

## 8. Required Output: FOUNDATION_VALIDATION.md

The validation report must contain the following sections.

### 8.1 Metadata

Include:

* Phase and prompt identifier.
* Version.
* Validation date, if available.
* Repository or project context, when known.
* References to the input artifacts.
* Implementation status reported by P06.1.
* Final validation status.

### 8.2 Executive Summary

Summarize:

* Whether the technical foundation conforms to the approved architecture.
* Whether it is ready for incremental development.
* The most important findings.
* Any conditions that must be resolved before proceeding.

### 8.3 Validation Scope

Describe the foundation components examined and explicitly state that user-story functionality was not required.

Identify any parts of the foundation that could not be assessed.

### 8.4 Verification Results

For each relevant check, document:

* Criterion.
* Verification method or command.
* Result: `PASSED`, `FAILED`, `NOT_RUN`, or `BLOCKED`.
* Evidence.
* Limitations or observations.

### 8.5 Findings

List findings using the severity and evidence requirements from Section 6.

If no findings exist, state that no material findings were identified within the scope and evidence available. Do not imply that every possible risk has been eliminated.

### 8.6 Architecture Conformance

Summarize:

* Conforming decisions.
* Deviations and their approval status.
* Unresolved architectural conditions.
* Their impact on foundation readiness.

### 8.7 Security and Configuration Review

Summarize the security and configuration checks performed, any findings, and any checks that remain unverified.

### 8.8 Implementation Log Accuracy

Identify any differences between the log and the actual repository, including unsupported claims or missing evidence.

### 8.9 Readiness Assessment

Assess whether the repository is ready to support incremental user-story implementation.

Explicitly separate:

* Technical foundation readiness.
* Outstanding warnings or conditions.
* Product functionality that remains intentionally unimplemented.

### 8.10 Required Corrective Actions

For each finding that prevents approval or requires follow-up, describe:

* Required correction.
* Reason.
* Verification criteria.
* Whether the action must be completed before proceeding.

Distinguish mandatory corrections from optional improvements.

### 8.11 Final Decision

Choose exactly one status:

* `PASS` — the foundation conforms to the approved architecture and is ready for incremental development. No material unresolved issue prevents proceeding.
* `PASS_WITH_WARNINGS` — the foundation is ready for incremental development, but documented non-blocking issues, limitations, or conditions require tracking. State explicitly whether any condition must be satisfied before proceeding.
* `FAIL` — material defects or non-conformance require corrective implementation and revalidation before the foundation can be approved.
* `BLOCKED` — a missing prerequisite, unresolved critical architectural issue, or insufficient evidence prevents a reliable validation decision.

Do not use `PASS_WITH_WARNINGS` to bypass a critical blocker or a material defect that prevents readiness.

## 9. Decision Rules and Pipeline Transition

Apply these rules consistently:

* `PASS`: P06.1 is approved as the technical foundation. The team may proceed to P06.3 for incremental user-story implementation.
* `PASS_WITH_WARNINGS`: proceed only if the remaining issues do not prevent safe incremental development and all explicitly required conditions have been satisfied. Track remaining warnings.
* `FAIL`: correct the identified issues in the foundation and repeat the relevant validation. Do not begin incremental implementation against an unapproved foundation.
* `BLOCKED`: resolve the prerequisite or evidence blocker before reaching an approval decision.

P06.2 is a validation gate within P06, not an independent pipeline phase.

After the foundation is approved, P06.3 and P06.4 handle implementation and validation of individual user stories. P07 remains responsible for broader product testing after the planned implementation scope is completed.

Before delivering the report, confirm:

* [ ] The actual repository was inspected.
* [ ] The implementation log was checked against actual files and results.
* [ ] Architecture approval and unresolved conditions were reviewed.
* [ ] The foundation was evaluated against applicable architectural decisions.
* [ ] Missing user stories were not incorrectly treated as defects.
* [ ] Security, configuration, maintainability, and readiness were evaluated as applicable.
* [ ] Executed and unexecuted checks are clearly distinguished.
* [ ] Material findings contain evidence and actionable corrections.
* [ ] Optional recommendations are distinguished from mandatory corrections.
* [ ] The final status follows the decision rules.
* [ ] `FOUNDATION_VALIDATION.md` records the basis for the decision.

The validation must be evidence-based, reproducible to the extent possible, and explicit about what was and was not verified.
