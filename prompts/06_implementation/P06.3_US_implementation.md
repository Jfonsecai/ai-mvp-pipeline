# P06.3 — Incremental User Story Implementation

**Version:** 1.0
**Phase:** P06 — Implementation
**Type:** Code generation
**Execution mode:** One selected user story per execution

## 1. Objective

Implement one selected user story in the existing repository, extending the approved technical foundation and preserving consistency with the product requirements, backlog, architecture, and UX specification.

Each execution must focus on exactly one user story identified by its authoritative ID, such as `US-020`.

The implementation must cover the selected story's applicable acceptance criteria, business rules, and edge cases to the extent supported by the approved inputs and satisfied dependencies.

**Do not implement multiple user stories in one execution. Do not treat this prompt as authorization to re-plan the backlog, change the architecture unilaterally, or implement unrelated features.**

## 2. Required Inputs

Read and use the following sources:

1. `prompts/system/SYSTEM_PROMPT.md`
2. `artifacts/03_planning/PRIORITIZATION.md`
3. `artifacts/03_planning/product_backlog.json`
4. `artifacts/02_requirements/REQUIREMENTS.md`
5. `artifacts/05_architecture/ARCHITECTURE.md`
6. `artifacts/05_architecture/ARCHITECTURE_VALIDATION.md`
7. `artifacts/04_ux/UX_SPEC.md`
8. `artifacts/04_ux/UX_SPEC_VALIDATION.md`
9. `artifacts/06_implementation/IMPLEMENTATION_LOG.md`
10. `artifacts/06_implementation/FOUNDATION_VALIDATION.md`
11. `artifacts/06_implementation/IMPLEMENTATION_INDEX.md`, if it exists.
12. Existing implementation logs and validation reports relevant to the selected HU and its dependencies, if any.
13. The actual current repository: source code, configuration, dependency manifests, tests, scripts, and documentation.

Additionally, the execution must identify exactly one selected user story by its ID. The selected HU must be found in the authoritative `product_backlog.json`.

If the execution environment supplies a selected HU document or an explicit HU ID, use it to locate the corresponding story in the backlog. Do not rely on a manually copied story description when it conflicts with the authoritative backlog.

If a required input is missing, unreadable, or inconsistent, document the issue and determine whether implementation can proceed safely.

## 3. Preconditions and Blocking Conditions

Before modifying code:

1. Verify that `FOUNDATION_VALIDATION.md` reports `PASS` or an eligible `PASS_WITH_WARNINGS`.
2. If the foundation was approved with warnings, confirm that none of the outstanding conditions prevents implementing the selected HU.
3. Confirm that the selected HU exists in the current authoritative backlog.
4. Inspect the HU's requirements, acceptance criteria, business rules, edge cases, assumptions, and dependencies.
5. Check the relevant prioritization or sprint plan to understand its current scope and position.
6. Review the actual repository and existing implementation records.
7. Determine whether prerequisite stories, shared components, or external dependencies are available and sufficiently validated.

Use `BLOCKED` when a prerequisite, missing decision, unresolved material assumption, or unavailable dependency prevents responsible implementation.

Do not silently bypass an unresolved dependency or material product decision. If a dependency is marked as unresolved, not implemented, failed validation, or otherwise unavailable, assess whether the selected HU can be implemented independently without violating its contract. If not, stop and document the blocker.

Do not implement a substitute behavior simply to make the story appear complete.

## 4. Authoritative Sources and Conflict Resolution

Use the artifacts according to their purpose:

* `product_backlog.json` is the authoritative source for the selected HU's ID, story description, acceptance criteria, business rules, edge cases, dependencies, and current backlog status.
* `REQUIREMENTS.md` provides the approved functional and non-functional requirements referenced by the HU.
* `PRIORITIZATION.md` provides delivery context, priority, and sprint planning.
* `ARCHITECTURE.md` defines approved technical decisions and component boundaries.
* `ARCHITECTURE_VALIDATION.md` records the architecture's validation status and conditions.
* `UX_SPEC.md` and its validation report define the applicable interaction and interface expectations.
* The approved foundation and actual repository define the existing technical baseline.
* Prior implementation logs and validation reports provide traceability and evidence about previous increments.

Do not silently reconcile contradictory artifacts. Identify the conflict, its impact, and the source that requires clarification or correction.

Preserve authoritative IDs. Do not invent, rename, delete, or reuse IDs for requirements, user stories, acceptance criteria, business rules, dependencies, or related artifacts.

If an implementation requires a new technical decision not established by the approved architecture, choose a minimally consequential and compatible option only when it does not materially change the approved design or product behavior. Record the assumption and its impact. If the decision is material, stop and request resolution.

## 5. Implementation Boundaries

### 5.1 Included

For the selected HU only:

* Implement the functionality needed to satisfy its approved acceptance criteria.
* Add or modify the relevant UI, API, services, domain logic, persistence, configuration, and integration code as required by the architecture.
* Apply the associated business rules and supported edge cases.
* Add or update automated tests relevant to the selected functionality when the repository supports them.
* Integrate with previously implemented and validated components.
* Update relevant technical documentation when necessary.
* Execute appropriate local checks and regression checks.
* Record implementation evidence in the HU-specific implementation log.

A user story may require changes across several technical layers. Implement the complete vertical slice required by the story instead of stopping at an isolated frontend, backend, or database component when the acceptance criteria require an integrated behavior.

### 5.2 Excluded

Do not:

* Implement unrelated user stories.
* Expand the selected HU's scope with unapproved features.
* Change acceptance criteria to match the implementation.
* Modify the architecture without documenting the deviation and obtaining required approval.
* Rewrite unrelated modules or perform broad refactoring without a clear necessity.
* introduce dependencies, infrastructure, or product behavior without justification.
* Mark a criterion complete merely because the relevant file or component exists.
* Claim functionality works without appropriate evidence.
* Modify prior validation reports to hide previous failures or warnings.

If a necessary change affects shared infrastructure or another story, make only the minimum justified change and document its scope, rationale, and impact. If it requires a material architectural change or changes another HU's contract, stop and request resolution.

## 6. Implementation Principles

1. **One HU per execution:** the selected story is the only product feature scope for this run.
2. **Acceptance-criteria-driven:** implementation decisions must be connected to the selected HU's criteria and applicable business rules.
3. **Architecture conformance:** use the approved foundation, patterns, and component boundaries.
4. **Minimal sufficient change:** modify only what is needed for the selected HU and necessary integration.
5. **Incremental integration:** reuse existing components and preserve working functionality.
6. **Traceability:** identify the HU, requirements, acceptance criteria, rules, and dependencies associated with material changes.
7. **Security and data integrity:** validate inputs, handle errors, and protect sensitive data according to applicable requirements and architecture.
8. **No invented behavior:** do not silently resolve material product ambiguity.
9. **Reproducibility:** document the relevant commands and configuration needed to verify the increment.
10. **Honest reporting:** distinguish implementation completed, tests passed, tests failed, checks not run, assumptions, and blocked work.

## 7. Execution Process

### Step 1 — Identify and inspect the selected HU

Locate the exact HU in `product_backlog.json`.

Extract and preserve:

* HU ID and title.
* Epic or parent grouping, if defined.
* User story description.
* Referenced requirement IDs.
* Acceptance criterion IDs and complete criterion text.
* Business rule IDs.
* Edge case IDs.
* Dependencies.
* Scope or release designation, if present.
* Backlog status.
* Assumptions, open questions, and relevant planning context.

Do not omit criteria because they appear difficult or require more than one technical layer.

### Step 2 — Assess readiness

Evaluate whether the HU can be implemented with the approved foundation and currently available dependencies.

Check whether:

* The HU's material assumptions are sufficiently resolved.
* Its required decisions have been approved.
* Dependencies have been implemented or otherwise satisfied.
* UX and architecture provide enough detail for the affected behavior.
* Existing code provides the required integration points.

If a material ambiguity or unresolved dependency prevents implementation, document the exact issue and return `BLOCKED`.

### Step 3 — Plan the technical increment

Before editing code, derive a concise implementation plan from the selected HU.

Identify:

* Technical layers and components involved.
* Existing modules to reuse or modify.
* New files or components required.
* Relevant data changes or migrations.
* API, UI, or integration changes, when applicable.
* Tests and verification checks needed for the acceptance criteria.
* Possible regressions or dependencies on shared functionality.

Break the story into technical tasks internally as needed. These tasks are execution aids; do not create a separate persistent technical-task backlog unless the project explicitly requires one.

Do not create unnecessary abstractions or placeholder tasks.

### Step 4 — Implement the selected HU

Modify the actual repository to implement the approved functionality.

Follow established project conventions and the approved architecture. Preserve existing work and avoid unrelated changes.

When the HU requires multiple components to work together, implement and integrate them sufficiently to satisfy the relevant acceptance criteria.

If new requirements or architectural conflicts emerge during implementation, stop the affected work, document the evidence, and reassess whether the HU is blocked.

### Step 5 — Add and execute verification checks

Create or update appropriate automated tests when feasible.

Execute relevant checks, which may include:

* Compilation, build, or static analysis.
* Unit tests.
* Integration tests.
* API or component tests.
* Database migration or persistence checks.
* Relevant frontend checks.
* Targeted regression checks.
* Other commands appropriate to the changed code.

Choose checks according to the actual implementation and repository capabilities. Do not claim that a test exists or passed unless that is true.

For each acceptance criterion, identify the available evidence. If direct verification is not feasible, explain why and mark the criterion as not verified rather than treating it as satisfied.

P06.3 checks are implementation-level verification. They do not replace the independent validation in P06.4 or the broader product-testing phase in P07.

### Step 6 — Review the change set

Before finalizing:

* Inspect the changed files and, when available, the version-control diff.
* Confirm that changes are limited to the selected HU and justified integration work.
* Check that no secrets or sensitive configuration have been introduced.
* Verify that documentation and tests match the actual behavior.
* Identify incomplete criteria, failures, assumptions, and remaining risks.
* Ensure that the repository remains in a coherent state.

Do not revert unrelated pre-existing work. If the repository contains unrelated uncommitted changes, preserve them and clearly distinguish them from the changes made for this HU.

### Step 7 — Create the HU-specific implementation log

Create or update:

`artifacts/06_implementation/increments/US-XXX_IMPLEMENTATION_LOG.md`

Replace `US-XXX` with the exact ID of the selected HU. Preserve the ID's canonical spelling and format from the backlog.

The log must document the implementation attempt, including partial or blocked work. Do not omit the log merely because implementation failed or could not start.

### Step 8 — Update the implementation index

Create or update:

`artifacts/06_implementation/IMPLEMENTATION_INDEX.md`

Preserve existing entries. Add or update only the entry for the selected HU.

The index is a cumulative summary of implementation and validation status. Do not treat a missing entry as proof that a HU was never attempted; inspect the relevant logs when necessary.

## 8. Required Output A: HU Implementation Log

The file `US-XXX_IMPLEMENTATION_LOG.md` must contain the following sections.

### 8.1 Metadata and Traceability

Include:

* Phase and prompt identifier.
* Version.
* Execution date, if available.
* HU ID and title.
* Epic or parent grouping, if defined.
* Backlog source path.
* Relevant requirement IDs.
* Acceptance criterion IDs.
* Business rule IDs.
* Edge case IDs.
* Dependency IDs.
* Relevant architecture and UX artifact paths.
* Foundation validation status.
* Implementation status.

Preserve the original IDs exactly as defined by the authoritative sources.

### 8.2 Story Summary and Scope

Summarize the selected HU and clearly state:

* What functionality was in scope.
* What was explicitly excluded.
* Which criteria and rules apply.
* Any material dependencies or assumptions.

Do not rewrite the story or its acceptance criteria. Reference the authoritative text and provide a concise summary where useful.

### 8.3 Readiness Assessment

Record:

* Whether implementation could proceed.
* Relevant dependency states.
* Material assumptions or unresolved decisions.
* Any blockers and their evidence.
* The reason implementation was continued, partially completed, or stopped.

### 8.4 Technical Implementation Plan

Summarize the planned technical tasks, affected layers, and intended verification.

Distinguish the initial plan from the changes actually completed.

### 8.5 Implemented Changes

For each significant change, record:

* Component or file path.
* Change made.
* Purpose.
* Related acceptance criteria, rules, or requirements.
* Relevant technical or architectural considerations.

Identify changes that support shared functionality and explain why they were necessary for this HU.

### 8.6 Acceptance Criteria Coverage

List every acceptance criterion from the selected HU using its original ID and text or a faithful reference to the authoritative source.

For each criterion, record:

* Implementation state: `IMPLEMENTED`, `PARTIALLY_IMPLEMENTED`, `NOT_IMPLEMENTED`, or `BLOCKED`.
* Files or components involved.
* Verification performed, if any.
* Evidence or reason it remains incomplete.

`IMPLEMENTED` means code intended to satisfy the criterion has been added; it does not mean the criterion has independently passed validation. P06.4 determines whether the evidence supports acceptance.

### 8.7 Business Rules, Edge Cases, and Dependencies

For each applicable rule, edge case, and dependency, document its treatment and evidence.

Identify any behavior that remains unimplemented or unverified.

Do not invent expected behavior for unresolved edge cases.

### 8.8 Tests and Verification Results

For each executed check, include:

* Check name.
* Command or procedure.
* Result: `PASSED`, `FAILED`, `NOT_RUN`, or `BLOCKED`.
* Relevant output or evidence.
* Limitations, if applicable.

Distinguish tests added from tests executed. Record any failed or unavailable checks.

### 8.9 Repository Changes

Summarize:

* Files created.
* Files modified.
* Files deleted, if any, with justification.
* Database migrations or configuration changes, if applicable.
* Relevant change-set or commit reference, if available.

Do not invent commit identifiers.

### 8.10 Architecture Conformance and Deviations

Document conformance with the approved architecture and any deviations.

State whether a deviation is merely a documented implementation detail or requires formal architectural review. Do not present unapproved material changes as accepted.

### 8.11 Assumptions, Risks, and Outstanding Work

For each item, include its description, impact, evidence, and required next action.

Distinguish:

* Product assumptions.
* Technical assumptions.
* Known defects.
* Unverified behavior.
* External limitations.
* Follow-up work outside this HU's scope.

### 8.12 Final Implementation Status

Choose exactly one status:

* `READY_FOR_VALIDATION` — the implementation is complete enough to undergo independent validation. This does not mean the HU has passed.
* `READY_WITH_LIMITATIONS` — an increment exists and can be validated, but documented non-blocking limitations or unverified checks remain. Explain their impact.
* `BLOCKED` — a material prerequisite, unresolved decision, or dependency prevents responsible completion or reliable validation of the increment.

Do not use `READY_WITH_LIMITATIONS` when a known critical defect or unresolved material decision makes validation unsafe or meaningless.

### 8.13 Handoff to P06.4

Provide:

* The exact HU ID and authoritative backlog location.
* The criteria implemented or partially implemented.
* Relevant files and components.
* Commands and results.
* Known limitations and assumptions.
* Specific behaviors that require independent verification.

## 9. Required Output B: Implementation Index

Create or update `artifacts/06_implementation/IMPLEMENTATION_INDEX.md`.

Maintain one entry per HU that has an implementation attempt or recorded implementation history.

Include, at minimum:

| Field                 | Description                                                     |
| --------------------- | --------------------------------------------------------------- |
| HU ID                 | Canonical ID from the backlog                                   |
| HU title              | Current authoritative title                                     |
| Priority / sprint     | When defined in the planning artifacts                          |
| Implementation status | Status from the latest implementation log                       |
| Validation status     | Latest P06.4 status, or `NOT_VALIDATED`                         |
| Implementation log    | Relative path to the HU log                                     |
| Validation report     | Relative path to the latest validation report, or `NOT_CREATED` |
| Blockers / warnings   | Concise summary of outstanding issues                           |
| Last updated          | Date, when available                                            |

Index rules:

* Preserve existing entries for other HUs.
* Never replace the full index with only the currently selected HU.
* Do not mark an HU as validated based on the implementation log.
* Do not infer that a previous implementation attempt passed validation.
* Keep implementation and validation statuses separate.
* When a HU is reimplemented, update its current status and references while preserving historical reports or prior evidence when available.
* If the index does not exist, create it and document that it was initialized during this execution.

## 11. Pipeline Transition

P06.3 does not independently approve the HU.

* If the status is `READY_FOR_VALIDATION` or `READY_WITH_LIMITATIONS`, invoke P06.4 for the same HU ID.
* If the status is `BLOCKED`, resolve the blocker before treating the HU as ready for validation.
* If P06.4 returns `FAIL`, correct the implementation and repeat the relevant validation.
* If P06.4 returns `BLOCKED`, resolve the blocker before reaching a validation decision.
* If P06.4 returns `PASS` or an eligible `PASS_WITH_WARNINGS`, record the validation result and assess readiness to proceed to another HU.

Do not automatically implement the next HU. Its dependencies, priority, and readiness must be checked against the current backlog and planning artifacts.

After the planned implementation scope is complete, proceed to P07 for broader product testing according to the pipeline's transition rules.
